# jenkins-certbot-letsencrypt

Jenkins pipeline that issues a Let's Encrypt certificate via DNS-01 validation
against Route53, and publishes the resulting cert files to S3.

It uses the official `certbot-dns-route53` plugin rather than hand-rolled
`aws route53` calls — the plugin finds the hosted zone, creates the
`_acme-challenge` TXT record, waits for it to propagate, and deletes it again
once the CA has validated the challenge. That's the "create and delete the
challenge record" requirement, handled by well-tested upstream code instead of
custom scripting.

## Security posture — read this first

**Nothing secret lives in this repo, the Jenkinsfile, or the CloudFormation
template.** The only two sensitive values the pipeline needs — an AWS access
key ID and secret access key — are:

- generated by the CloudFormation stack (section 2) and written straight into
  **AWS Secrets Manager**, never into a stack Output, the template, or
  CloudTrail-visible `describe-stacks` output, and
- from there copied once into **Jenkins' own credential store** (section 2,
  step 4) as two `Secret text` credentials, referenced by ID (not value) from
  the `Jenkinsfile` parameters.

Everything else in this repo (example bucket names, zone IDs, email
addresses) is a non-sensitive placeholder you edit for your environment — if
you add anything new, keep following that rule: secrets are a Jenkins
credential ID or a Secrets Manager ARN, never a literal in a parameter
`defaultValue`.

## 1. Jenkins prerequisites

- **Credentials Binding plugin** — ships with Jenkins core almost everywhere;
  no extra install needed.
- A **Linux** agent with `python3` (with the `venv` module) and `bash`. No
  root required — `aws-cli` and `certbot` are installed into a throwaway
  virtualenv (`.venv/`) per workspace, not system-wide.
- Outbound network access from the agent to `pypi.org` (tool install),
  AWS APIs, and Let's Encrypt's ACME endpoints (`acme-v02.api.letsencrypt.org`
  and, when `ACME_SERVER=staging`, `acme-staging-v02.api.letsencrypt.org`).
  If the agent sits behind a proxy/firewall, make sure those are allow-listed.

## 2. AWS setup — CloudFormation (recommended)

`cloudformation/jenkins-certbot-infra.yaml` creates everything AWS-side in
one stack:

- the S3 bucket (encrypted, versioned, public access blocked, with the
  `_healthcheck/` lifecycle-expiry rule below)
- a least-privilege managed IAM policy (same permissions as `iam-policy.json`,
  but templated instead of hand-edited)
- the IAM user, with that policy attached
- an IAM access key for that user
- a Secrets Manager secret holding `{AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY}`
  — this is the only place the secret value is ever written

Deploy it:

```bash
aws cloudformation deploy \
  --stack-name jenkins-certbot-letsencrypt \
  --template-file cloudformation/jenkins-certbot-infra.yaml \
  --capabilities CAPABILITY_NAMED_IAM \
  --parameter-overrides \
      DomainName=example.com \
      HostedZoneId=Z0123456789ABCDEFGHIJ \
      S3BucketName=my-certbot-cert-bucket \
      IAMUserName=jenkins-certbot
```

If you already have a bucket you want to reuse instead of creating a new one,
add `CreateS3Bucket=false` — the IAM policy still scopes to `S3BucketName`.

Then, **once**, pull the generated credentials out of Secrets Manager:

```bash
aws secretsmanager get-secret-value \
  --secret-id jenkins-certbot-aws-credentials \
  --query SecretString --output text
```

4. In Jenkins, create two **Secret text** credentials from that output:
   - `aws-certbot-access-key-id` → the `AWS_ACCESS_KEY_ID` value
   - `aws-certbot-secret-access-key` → the `AWS_SECRET_ACCESS_KEY` value
   (these IDs are the defaults for the `AWS_ACCESS_KEY_CRED_ID` /
   `AWS_SECRET_KEY_CRED_ID` job parameters — change either side if you'd
   rather use different credential IDs.)

   For a hands-off alternative, install the **AWS Secrets Manager
   Credentials Provider** Jenkins plugin and point it at this secret — Jenkins
   will expose it as a credential automatically, with no copy/paste step at
   all.

> Caveat: embedding `${AccessKey.SecretAccessKey}` in a `SecretString` via
> `Fn::Sub` is the standard CloudFormation pattern for this (it's never
> exposed via Outputs or `DescribeStacks`), but the `secretsmanager:CreateSecret`
> call CloudFormation makes is still a CloudTrail management event. If your
> compliance posture needs CloudTrail itself to never see the value, create
> the access key out-of-band (`aws iam create-access-key`) and skip the
> `CertbotAccessKey`/`CertbotCredentialsSecret` resources.

### AWS setup — manual (alternative)

If you'd rather not use CloudFormation, do it by hand:

1. Create an IAM user (e.g. `jenkins-certbot`) for programmatic access only.
2. Attach a policy based on `iam-policy.json` in this repo, after replacing
   `YOUR_HOSTED_ZONE_ID` and `YOUR_BUCKET_NAME` with your real values.
3. Generate an access key for that user (`aws iam create-access-key`).
4. Create the same two Jenkins `Secret text` credentials described above.

Either way, the policy grants exactly:
- `route53:ListHostedZones`, `route53:ListHostedZonesByName` (account-wide —
  Route53 doesn't support resource-scoping these)
- `route53:GetHostedZone`, `route53:ListResourceRecordSets`,
  `route53:ChangeResourceRecordSets` — scoped to the one hosted zone
- `route53:GetChange` — needed by certbot to poll until the record change
  is `INSYNC`
- `s3:ListBucket` — scoped to the one bucket (used by the pipeline's
  healthcheck step)
- `s3:PutObject`, `s3:GetObject` — scoped to objects in that bucket
- `sts:GetCallerIdentity` — used to verify the credentials are live

Deliberately **no** `s3:DeleteObject` is granted, per the brief's least-
privilege ask. The pipeline's S3 permission check (`Validate S3 Permissions`
stage) writes a small marker object under `<prefix>/_healthcheck/` every
build and never deletes it — the CloudFormation stack's bucket already has a
lifecycle rule to expire that prefix after 1 day; if you created the bucket
by hand, add the same rule yourself:

```json
{
  "Rules": [{
    "ID": "expire-jenkins-certbot-healthchecks",
    "Filter": { "Prefix": "certificates/_healthcheck/" },
    "Status": "Enabled",
    "Expiration": { "Days": 1 }
  }]
}
```

## 3. Create the pipeline job

Create a Pipeline job pointing at this repo (or paste `Jenkinsfile` directly
into a Pipeline script). On first run, Jenkins will discover the `parameters {}`
block and expose it as a normal "Build with Parameters" form (dropdown for
`DOMAIN_NAME`, checkbox for wildcard, etc.) from the second build onward.

## 4. Parameters

| Parameter | Purpose |
|---|---|
| `DOMAIN_NAME` | Dropdown of pre-set domains, or `CUSTOM` |
| `CUSTOM_DOMAIN_NAME` | Free-text domain, only read when `DOMAIN_NAME=CUSTOM` |
| `INCLUDE_WILDCARD` | Also request `*.<domain>` as a SAN |
| `HOSTED_ZONE_ID` | Route53 zone ID containing the domain (validated before certbot runs) |
| `S3_BUCKET_NAME` / `S3_PREFIX` | Where issued certs are uploaded |
| `AWS_REGION` | Region for S3/STS calls (Route53 API itself is global) |
| `LETSENCRYPT_EMAIL` | Registration + expiry-notice address |
| `ACME_SERVER` | `production` (default) or `staging` — **switch to staging while testing** |
| `CERT_KEY_TYPE` | `rsa` (default, 2048-bit) or `ecdsa` (secp384r1) |
| `AWS_ACCESS_KEY_CRED_ID` / `AWS_SECRET_KEY_CRED_ID` | Jenkins credential IDs from step 2 — point at the Secrets Manager values, never literal keys |
| `CERTBOT_BASE_DIR` | Optional absolute host path to persist certbot state across builds (see below) |

Edit the `choices` list for `DOMAIN_NAME` and the various `defaultValue`s in
the `Jenkinsfile` to match your real domains/bucket/zone before running.

## 5. Things worth knowing that weren't explicit in the ask

- **Rate limits**: Let's Encrypt production allows 5 duplicate certificate
  requests per exact domain set per week, and 50 certs per registered domain
  per week. `ACME_SERVER` defaults to `production`, so switch it to `staging`
  the first few times you run or change this pipeline.
- **State persistence / renewal**: certbot tracks its account registration
  and renewal config under its config dir. By default this pipeline keeps
  that under the job workspace (`.certbot/`), which is fine for one-shot
  issuance but may be wiped by workspace cleanup between builds. Set
  `CERTBOT_BASE_DIR` to a stable path on the agent (e.g.
  `/var/lib/jenkins-certbot`) if you want certbot to recognize this as a
  renewal of a cert it already issued rather than a brand-new request every
  time.
- **Concurrency**: `disableConcurrentBuilds()` is set so two builds can't
  race to create/delete the same `_acme-challenge` TXT record.
- **Private key handling**: the private key is uploaded to S3 with
  `--sse AES256` and is explicitly excluded from Jenkins' `archiveArtifacts`
  (only `*.log` files under the certbot logs dir are archived) — Jenkins
  build artifacts are visible to anyone with job read access, which is the
  wrong place for key material.
- **Domain/zone ownership check**: the `Validate Route53 Permissions` stage
  confirms `DOMAIN_NAME` actually falls under `HOSTED_ZONE_ID` before
  spending an ACME rate-limit slot on a request that would fail anyway.
- **Timeout**: the whole pipeline is capped at 30 minutes in case DNS
  propagation or ACME validation hangs.
- **Key type**: `CERT_KEY_TYPE` defaults to `rsa` (2048-bit); pick `ecdsa`
  (secp384r1) if your downstream services prefer smaller/faster EC certs.
- **Not included, consider separately**: a scheduled (`cron`) trigger to
  re-run this monthly for renewal; Slack/email notification on failure or on
  approaching expiry; multi-domain/SAN lists beyond the single wildcard
  toggle.
